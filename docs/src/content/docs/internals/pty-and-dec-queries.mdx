`zmux.NativeSession` provides a real PTY and a raw byte ring buffer, but it does not emulate a terminal state machine. When Claude Code starts, Ink probes the terminal for capabilities, cursor position, and viewport dimensions. If nothing answers those queries, Ink blocks and `SessionStart` never fires.

## Wire grammar (`src/terminal.zig`)

`terminal.respondToDecQueries(allocator, bytes, out)` scans each incoming PTY chunk for CSI sequences (`0x1b '['`, optional private `'>'`, parameter bytes `0x30..0x3f`, intermediate bytes `0x20..0x2f`, final byte) and appends any matching reply to `out`.

<VtByteGrammarDiagram />

All non-matching bytes and non-query CSI sequences are ignored. The scanner holds no state between calls, so it is thread-safe by construction and verified by unit tests in `src/terminal.zig`.

## Why no full VT emulator?

An early prototype considered embedding `libghostty-vt` to maintain a screen grid and read replies off the rendered terminal. Once `Stop` hooks and JSONL transcript parsing replaced screen scraping, `claude-p` needed only two operations on PTY bytes:

1. Answer the five startup probes (`src/terminal.zig`, ~65 lines).
2. Strip CSI, OSC, and DCS escapes into a stack buffer (`driver.stripCsiInto`) so the startup dialog handler can inspect plain text and the `❯` cursor.

If a future Claude Code release adds a new boot probe, the failure surfaces as `SessionStartTimeout` (visible under `--debug`), and the fix is one `switch` arm in `src/terminal.zig`.
